# Задание агенту: сидирование контура Бердниковой

Цель: на уже включённых `ledger` + `acquisition` + `rates` + `fp_berd` заполнить справочники и биндинги так, чтобы работали первичная разметка, ROMI по каналам, планы/нормы врачей и ФП (статьи↔ДПС, сценарий BE, недельные конверты).

**Не делать:** не трогать `funds` как %-конверты; не плодить CRM-сделки; не создавать мусорных клиентов без записи; не выдумывать новые типы таблиц.

**Текущий gap на инстансе (снимок):** источники привлечения пусты; планы сотрудников = 0; у статей FOT/OPEX `ID_TYPE=0`; у сценария «Базовый» нет строк; недельных конвертов нет. Уже есть ДПС `#48 Маркетинг`, `#49 Реклама / ROMI` и статьи MKT/ROMI на них.

## 1. ДПС (ledger) — что должно быть

Использовать **существующие** типы где возможно. Не плодить дубликаты с тем же `NAME`.

### 1.2. Политика биндинга (важно)

- Статья ФП `MKT`/`ROMI` должна смотреть на тип, **которым реально проводятся** рекламные ДПС.
  - Предпочтительно привязать **`MKT` → `#11 Реклама и продв.`** (живой факт), а `#48/#49` оставить как опциональные корзины или объединить: все новые рекламные платежи — через `#11`, а на ДПС ставить `source_id` канала (acquisition).
  - Если директор хочет отдельный тип «Маркетинг» — оставить `#48` и перевести новые платежи туда; тогда `MKT → 48`.
- `FOT` / `FOTA` → **развести в ledger**: `ФОТ врачи (банк)` (проценты + оклады медсестёр/врачей = себестоимость) и `ФОТ АУП (банк)` (директор/управляющий/ресепшен). Не держать всё в одном «Оплата труда (банк)» — иначе недельный факт нечитаем.
- `IT` / `HR` / `OPEX` → отдельные типы ДПС (`IT и телеком`, `Персонал и обучение`, `Прочие…`), не один catch-all.
- Migrator: `seed_fot_split_types` (создаёт типы + перекидывает legacy payroll по DESCR).
- Не создавать второй «Маркетинг», если `#48` уже есть.

### 1.3. Опционально создать (только если нет аналога)

Через `ledger.types.save` (`POST /account-move-types/new`), `direction=-1`, `enabled=1`, `pid` = id родительской группы расходов (на инстансе часто `pid=5`):

| NAME | Когда нужен |
|------|-------------|
| Агрегаторы (Профи/Яндекс) | Отдельный ROMI-срез от «своей» рекламы |
| Колл-трекинг / ВАТС | Расход телефонии как mkt |

Иначе достаточно `#11` + `source_id` на движении.

## 2. Статьи ФП (`fp_berd.articles`)

Минимальный полный набор (создать недостающие, обновить `type_id`):

| code | name | kind | type_id (рекомендация) |
|------|------|------|-------------------------|
| REV | Выручка операционная | rev | `#2` или суммарно оставить 0 и считать BE вручную |
| MKT | Маркетинг / реклама | mkt | **`11`** (или `48`) |
| FOT | ФОТ врачи / себестоимость | fot | **`ФОТ врачи (банк)`** |
| FOTA | ФОТ АУП | fot | **`ФОТ АУП (банк)`** |
| RENT | Аренда | opex | аренда |
| MAT | Материалы | opex | расходные |
| IT | IT и телеком | opex | **свой тип**, не «Прочие» |
| HR | Персонал и обучение | opex | **свой тип** |
| OPEX | Прочие операционные | opex | прочие |
| CAPEX | Кап. оборудование | capex | оборудование |
| DIV | Вывод прибыли учредителям | own | **`Вывод прибыли учредителям`** (входит в BE fixed) |

Ops:

- list: `GET /fp-berd/articles`
- create: `POST /fp-berd/articles/new` — body: `code,name,kind,type_id,sort,enabled=1`
- update: `POST /fp-berd/articles/{id}/edit`

Критерий готовности: у каждой статьи с `kind` ∈ {mkt,fot,opex,capex} `type_id > 0` (кроме осознанно «виртуальных»).

## 3. Сценарии + BE (как в таблицах Бердниковой)

Одного «Базовый» мало — в её демонстрациях обычно **три колонки/сценария** (что если…):

| Сценарий | Смысл | BE (демо-дефолт) | Множитель расходов |
|----------|--------|------------------|---------------------|
| Пессимистичный | Низкая загрузка | 2.2M | ~0.75× (MKT ~0.55×) |
| Базовый | План месяца | 3.0M | 1.0× |
| Оптимистичный | Амбициозный рост | 4.2M | ~1.25× (MKT ~1.4×) |

Быстрый путь (agent_token):

```bash
curl -sS -X POST -H "X-FreeSaaS-Agent-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"activate":"base"}' https://HOST/agent/fp-berd/seed-demo
```

Ручной путь: `POST /agent/fp-berd/scenarios` или UI `/fp-berd/scenarios` — у каждого сценария `lines[]` с `amount`/`pct` по статьям.

Цифры BE на клинике — **спросить директора** или подставить фактом (`be_low`/`be_base`/`be_high` в body seed).

Проверка: `GET /agent/fp-berd/be` → `ok=true`, `fixed_opex > 0`, `lines` не пустые; `GET /agent/fp-berd/scenarios` → три имени.

## 4. Недельные конверты (`fp_berd.weeks`)

На текущую неделю (понедельник):

1. Для каждой статьи с планом создать envelope: `week_start`, `article_id`, `scenario_id`, `plan_amount` ≈ месячный amount / 4.3 (или явная недельная квота директора).
2. `POST /fp-berd/weeks` с `refresh_facts=1` — подтянуть факт из ДПС по `ID_TYPE` статьи.

Критерий: `GET /fp-berd/weeks?week=YYYY-MM-DD` → строки с `plan_amount` и обновлённым `fact_amount`.

### 5.2. Обращения

- Не обязательно массово сидить историю.
- Для проверки контура: 2–3 `POST /acquisition/calls/new` с разными `result_id` (0 unmarked, 2 booked, 3 lost).
- На новых клиентах после визита: `source_id` через карточку клиента (секция acquisition).

### 5.3. ROMI на ДПС

При создании/правке расходного движения маркетинга (`POST /ledger/moves/new` / edit):

- `type_id` = тип статьи MKT (11 или 48),
- `source_id` = id источника из §5.1.

Без `source_id` BI `romi_by_source` пустой.

## 6. Rates — планы / нормы (`/rates/plans`)

На текущий `period_ym=YYYY-MM` для **работающих специалистов с ставками** (не роботы/стажёры без плана):

`POST /rates/plans/new`:

| field | смысл |
|-------|--------|
| operator_id | staff id |
| period_ym | YYYY-MM |
| plan_sum | план выручки ₽/месяц |
| norm_rub_hour | норма ₽/час |
| bonus_tiers | строки `from:pct`, напр. `500000:5` / `800000:8` |
| note | опционально |

Цифры — спросить директора или оценить по выручке процедур прошлого месяца (`procedures` / BI `doctor_avg_check`). Не ставить одинаковый план всем без причины.

Критерий: `GET /rates/plans?period_ym=…` → ≥1 план на ключевых врачей.
